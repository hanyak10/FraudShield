Getting Started

What FraudShield Is

🎯

In one line: FraudShield watches every payment as it happens, decides within milliseconds whether it looks fraudulent, and instantly warns the user if something is wrong — exactly like the fraud systems running behind banks, Stripe, PayPal, and Paytm.

The Problem It Solves

When you swipe a card or tap "pay," a bank has a fraction of a second to decide: is this really you, or is this a stolen card? If they are too slow, fraud goes through and the bank loses money. If they are too aggressive, they block real customers and everyone gets annoyed. Doing this well, at the scale of thousands of payments per second, is one of the hardest problems in financial software.

FraudShield is a working model of that system. It is a backend platform (no real money involved — all data is mocked) that receives payment events, scores each one against a set of fraud rules, and raises an alert the moment something looks suspicious.

What It Actually Does — Step by Step

Imagine a customer named Priya. Here is what FraudShield does the instant a payment on her account comes in:

  1. 1
    Receives the payment. A merchant's app sends a transaction — amount, currency, merchant, location — to FraudShield's secure API. The request must carry a valid login token, or it is rejected on the spot.
  2. 2
    Checks for fraud patterns. Is Priya suddenly making 6 payments in a minute? Is this payment 50× bigger than her usual spend? Is it coming from a country she has never shopped from before? Each suspicious signal adds to a "fraud score."
  3. 3
    Makes a decision. If the total score crosses a threshold, the payment is flagged. If not, it passes silently. This whole decision takes under a tenth of a second.
  4. 4
    Alerts the user. If flagged, Priya instantly gets a notification: "We noticed an unusual payment on your account." A human fraud analyst can also review it and override the decision.
  5. 5
    Records everything. Every payment, every decision, every analyst action is logged — so there is a complete, tamper-evident audit trail.

Who Uses It

Three kinds of people interact with FraudShield: end users (customers like Priya who receive alerts), payment clients (merchant apps that submit transactions), and fraud analysts (staff who review flagged payments and tune the detection rules).

Why This Project Exists

This is a learning and portfolio project. It is deliberately built the way a real fintech platform would be built — same architecture, same security layers, same failure-handling — so it can be used to understand and explain how production fraud systems actually work. It runs entirely on your own machine with fake data, so nothing real is at risk.

The Big Picture

Six Spring Boot microservices communicate through Apache Kafka and REST. The Transaction Service is the only public entry point. Everything else is internal. Redis underpins two cross-cutting concerns: sliding-window fraud counters and JWT token revocation.

The analytical core. Consumes raw-transactions, evaluates each against active rules from PostgreSQL, computes a composite score, persists the verdict, and publishes to fraud-verdicts. Velocity Check — Redis Sliding Window

ZADD velocity:{userId} {epochMs} {txId}
ZREMRANGEBYSCORE velocity:{userId} 0 {epochMs - 60000}
count = ZCARD velocity:{userId}
EXPIRE velocity:{userId} 60
if (count > 5) score += 40;
💡

Why a sorted set, not INCR? A fixed window resets at boundaries — an attacker could send 5 txns at 11:59:59 and 5 more at 12:00:01 and never trigger. Sorted sets give a true sliding window.

The identity backbone — the only service that issues tokens. Manages users, roles, password hashing, JWT generation, refresh rotation, and logout via Redis blacklisting. Other services validate JWTs locally without calling back; only the blacklist check hits shared storage.

How It Works

End-to-End Request Flow

Traces a single flagged transaction from the client's HTTP call to the user's email alert. This is what an interviewer expects when they ask "walk me through your system."

  1. 1
    Client Authentication: POST with Bearer JWT. Filter validates signature, expiry, Redis blacklist. 401 on failure.
  2. 2
    Payload Validation: Bean Validation checks fields. 400 with field errors on failure.
  3. 3
    Persist + Publish: Saved to PostgreSQL, published to Kafka. 202 returned after Kafka ACK.
  4. 4
    Rules Evaluation: Redis sliding window finds 6 txns/60s. Score = 70 → FLAGGED.
  5. 5
    Alert Creation: Alert Service creates alert, publishes to alert-notifications.
  6. 6
    User Notification: Worker checks idempotency key, sends mock email.

Handling an Unauthenticated Request

  1. 1
    Request arrives. JwtAuthenticationFilter runs before the controller.
  2. 2
    Filter checks for Bearer token. Absent → SecurityContext anonymous.
  3. 3
    Token validation: signature, expiry, Redis blacklist. Any failure → anonymous.
  4. 4
    Spring Security evaluates the route. Public routes pass; protected require auth.
  5. 5
    401 Unauthorized returned as structured JSON — no stack trace. Source IP logged.
🔐

401 vs 403: 401 = "not authenticated." 403 = "authenticated, no permission." FraudShield returns 401 for invalid tokens, 403 for insufficient roles.

Auth & Token Flow (Three Layers)

Token Refresh Flow

POST /api/auth/refresh { "refreshToken": "UUID" }
Server:
  1. Hash incoming token (SHA-256)
  2. Look up hash in PostgreSQL
  3. Check: not expired, not already used
  4. DELETE old refresh token (rotation — single use)
  5. Issue new JWT (15 min) + new refresh token (7 days)
  6. Invalid → 401, client must re-login
⚠️

Why single-use refresh tokens? If stolen and used by an attacker, the legitimate client's next refresh fails (already consumed) — alerting the system to theft. Both parties are forced to re-login.

Glossary

TermDefinition
JWTStateless, signed token carrying claims. No DB lookup to validate — just verify the signature.
Refresh TokenLong-lived single-use token (hashed in DB) to obtain new JWT pairs without re-login.
Token RotationEach refresh invalidates the old token and issues a new pair.
Token BlacklistRedis set of revoked JWT IDs (jti) with TTL. Honours logouts before natural expiry.
Kafka TopicNamed, ordered, append-only log of events. Producers write; consumer groups read.
Consumer GroupConsumers sharing a group ID. Kafka distributes partitions — one per consumer max.
Dead Letter TopicTopic for messages that failed processing after all retries.
IdempotencyAn operation producing the same result no matter how many times applied.
Sliding WindowTime-based counter over a rolling period. More accurate than a fixed window.
RBACRole-Based Access Control. Permissions on roles; roles on users.
Circuit BreakerStops calling a failing service, lets it recover, resumes once confirmed.
CQRSCommand Query Responsibility Segregation. Separates write from read models.
BCryptPassword hashing with a cost factor. Cost 12 ≈ 250ms per hash.
HPAKubernetes Horizontal Pod Autoscaler. Scales on CPU or custom metrics.
jtiJWT ID claim. Unique per token. Used as the Redis blacklist key.

FAQ

Why JWT and not server-side sessions?

Sessions require a shared store and a DB lookup per request. JWT is stateless — the server only needs the secret key. You can scale to 100 instances with no shared auth state. The only shared state we add back is the Redis blacklist, a conscious tradeoff for logout support.

Why Kafka over RabbitMQ or REST calls?

Retention and replay. Kafka keeps messages 7 days regardless of consumption. If Rules Engine is down for an hour, every transaction is waiting when it recovers — in order. RabbitMQ deletes on ACK. REST creates synchronous coupling.

How does the Rules Engine scale without double-processing?

Kafka consumer groups assign one partition to exactly one consumer, so instances partition the work without overlap. For rare redeliveries, the Redis idempotency key ensures double-processing is silently skipped.

What happens when an unauthenticated user hits a protected endpoint?

The JWT filter runs before any controller. With no valid token the SecurityContext stays anonymous and Spring Security returns 401 with structured JSON — no stack trace. The request is logged with source IP.

Why BCrypt cost factor 12?

Cost is exponential. Cost 10 ≈ 75ms (too fast, GPU-brute-forceable). Cost 14 ≈ 1000ms (too slow under load). Cost 12 ≈ 250ms — the sweet spot.

Why hash refresh tokens before storing?

If the DB is breached, plaintext refresh tokens let an attacker issue JWT pairs for every user. Hashing (SHA-256) gives the attacker only useless hashes. The raw token travels only over HTTPS.

How do you change fraud rules without redeploying?

Rules live in the fraud_rules table, not code. The Rules Engine re-queries every 60 seconds via a scheduled job. An analyst updates a threshold via the Admin API — it takes effect within 60 seconds, no restart.

Can I replace H2 with PostgreSQL in dev?

Yes. Set the profile to dev, run docker-compose up postgres, update the DB env vars. JPA DDL auto-create handles schema generation in both — the same entity classes work unchanged.
